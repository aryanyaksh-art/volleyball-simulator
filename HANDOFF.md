## Things that will bite you if you don't know them

### The pose rotation sign convention (already fixed, don't re-break it)

`poseRig.ts` is authored so a positive `x` means "swing forward, toward the net" and a positive `z` means "swing outward, away from the midline," the intuitive way to read a pose table. Three.js's actual rotation math does the opposite for both axes on a hanging limb. This was empirically verified, not derived on paper (paper derivation got the sign wrong twice before empirical testing settled it), by directly reading a joint's world-space direction via its `matrixWorld` and checking it against the net/midline.

The fix lives in `CapsuleHumanoid.setPose()`: it negates `x` and `z` for `spine`, `shoulderL/R`, and `hipL/R` before calling `rotation.set(...)`. The knees are the one joint that needed no correction: their natural "shin swings behind the thigh" bend already matched Three.js's math with a positive angle unchanged. If you add new poses or new joints, verify the direction empirically (set a single joint, read `matrixWorld`, check world position against something you know) before trusting a hand-derived sign.

### Shoulder rotation compounds with spine lean

`shoulderL/R` are children of `spine` in the hierarchy, so a spine forward lean adds to the shoulder's own forward swing, correctly, exactly like a real shoulder moving with a leaning torso. Each pose's authored shoulder angle is (desired total forward reach) minus (that pose's spine.x). If you tune a pose's spine lean, the shoulder angle needs to move with it or the arm will reach further (or less far) than intended. Hip angles do not need this treatment: the hip is a child of the pelvis, which never rotates.

### `preserveDrawingBuffer: true` is intentional

`SceneRenderer.ts` sets this on the WebGL context so `canvas.toDataURL()` works (used this session to capture reference screenshots) and so the Phase 7 PNG rotation-sheet export will work. Cheap for this scene's complexity. Don't remove it as a "perf cleanup."

### Dev-only debug hooks exist

`SceneCanvas.tsx` attaches `window.__appStore`, `window.__sceneBridge`, and `window.__sceneRenderer` to the page, gated behind `import.meta.env.DEV` (never ships in a prod build). These made it possible to drive poses/camera/theme and read back exact joint rotations from outside React, which is how the sign-convention bug above actually got found and fixed instead of just eyeballed. Keep using them for anything that needs precise verification rather than guessing from a screenshot.

### Testing in an automated browser: render-loop stalls

If you're driving the dev server through a headless/automated browser tool (as this session did), be aware: when the browser pane isn't the foreground/visible surface, `requestAnimationFrame` can stall, so the Three.js render loop stops advancing even though application state (Zustand store, Three.js object rotations) updates correctly and instantly. Symptom: you change a pose, take a screenshot, and it's pixel-identical to the previous one. The scene graph is right, the canvas just never repainted. Two things that reliably force a repaint: taking a `computer` screenshot action (not a JS-only call), and doing it inside the same batched call as the state change rather than as a separate subsequent tool call. Manually setting `camera.position` / calling `controls.update()` directly (bypassing the store's `goToCameraPreset`) seemed to make the stalling worse. Prefer driving the camera through the store when you need a reliable re-render during testing.

## What's done: Phase 3 (play model + playback) — core layer complete and tested, ship target verified live

- `core/play/types.ts` — `Play`/`PlayStep`/`Movement`/`BallSegment`/`PlayerRef`/`PositionRef` per the plan's symbolic-reference design.
- `core/play/schedule.ts` — the two structs of the core→render contract: `WorldState` (per frame) and `PlaySchedule`/`PlayerTrackSegment`/`BallTrackSegment` (per edit, absolute-time tracks after compile).
- `core/play/ballFlight.ts` — `ballHeightAt()` implements the plan's exact closed-form parabola (`y0 + (y1-y0)u + k·u(1-u)`) for a mid-flight apex, plus a two-piece quadratic variant for an asymmetric `apexU` (a spike's peak near contact) — both exact at every endpoint and at the apex, proven in `tests/ballFlight.test.ts`. `checkBallFlight()` gives net-clearance (`BALL_INTO_NET`, shortfall in cm), antenna (`BALL_OUTSIDE_ANTENNA`), and landing (`BALL_OUT`, warning not error) diagnostics — computed, tested, but **not surfaced in any UI yet**.
- `core/play/playerMotion.ts` — the speed-cap diagnostic the plan calls "the highest-value feature": `checkSpeedCap()` compares a move's required m/s against its mode's cap and suggests a duration that would fix it. Also computed and tested, **not wired into compile or any UI** — nothing in the demo play currently exceeds a cap, so there's nothing to see yet.
- `core/play/refs.ts` — resolves `PlayerRef` (slot/role/zone/libero) against a rotation's `LineupBreakdown`, and `PositionRef` (local/zoneAnchor/atPlayer/ballAt) against a `RefSnapshot` taken at the start of each step. Documented simplification: refs resolve against pre-step positions only, not "wherever a player will be later in this same step" — avoids needing iterative fixpoint resolution, matches how compile.ts walks steps sequentially anyway.
- `core/play/compile.ts` — `compilePlay()` flattens `Play.steps` into `PlaySchedule`, carrying forward each player's/the ball's position across steps and synthesizing "hold" segments for anyone not given a movement in a step, exactly as the plan specifies ("players not listed HOLD position").
- `core/play/evaluate.ts` — `evaluateInto()` is a pure function of `t`: no `dt` accumulation, no RNG, mutates `out`'s arrays in place rather than allocating. Verified deterministic in `tests/compile.test.ts` by sampling 200 values of `t` twice and asserting deep equality, and by confirming a scrub-directly-to-t result matches a step-through-to-t result.
- Moved `effectivePosition()` from `app/deriveRotationState.ts` into `core/court/anchors.ts` — it's pure domain logic (zone → position with override fallback) that `core/play/refs.ts` also needs, and `core/` can't import from `app/` (the boundary rule that caught this: first attempt at `refs.ts` imported it from `app/` and failed lint immediately).
- Tests: `tests/ballFlight.test.ts`, `tests/playerMotion.test.ts`, `tests/compile.test.ts`, `tests/diagnostics.test.ts`, `tests/waypoints.test.ts` — 65 tests total across the whole suite, all passing, `tsc -b` and `eslint .` clean.
- Render/playback wiring: `render/ball/BallVisual.ts` (a themed sphere), `SceneBridge.setBallState()`, `SceneRenderer.start()` now takes an optional `onFrame(dtSeconds)` callback — the one seam playback ticks through, keeping React out of the render loop per the plan's architecture rule. `app/store/usePlaybackStore.ts` holds `mode: 'formation' | 'play'`, `selectedPlayId`, `playing`/`t`/`durationS`/`speed`/`loop`/`diagnostics`. `SceneCanvas.tsx` compiles whichever play in `fixtures/demoPlays.ts` is selected against the live roster/lineup store (so editing the lineup panel changes what the play animates), and its `onFrame` callback owns advancing `t`, evaluating the schedule, and pushing the resulting `WorldState` into the scene — throttled to ~12 Hz sync back to the store for the scrub bar's display, full rAF rate for the actual scene update. `ui/TransportBar.tsx` — play selector dropdown, play/pause, scrub, speed (0.25×-2×), loop, and the formation/play mode toggle.
- `core/play/diagnostics.ts` — `diagnosePlay()` walks a compiled schedule and surfaces exactly the two checks the plan calls the highest-value feature: `checkSpeedCap()` against every non-hold player segment, `checkBallFlight()` against every ball segment (landing-out only checked for terminal contacts — serve/attack/tip/roll, not pass/set/dig). Recomputed alongside the schedule in `SceneCanvas`'s compile effect, shown live in `ui/panels/DiagnosticsPanel.tsx` (floating over the scene, visible only in play mode).

- `core/play/compile.ts` now honors `Movement.via`: each waypoint resolves against the same step-start snapshot as `to`, and the movement's total duration splits into one `PlayerTrackSegment` per leg, proportional to that leg's share of total path length (uniform speed without needing a spline). Facing holds steady through transit and only rotates to the target during the final leg. Not a Catmull-Rom curve — legs are straight, so the path has corners at each waypoint rather than a smooth curve — but a player routing via a waypoint no longer cuts a straight line through whatever was in the way. Combining `via` with `jump` isn't supported (a jump's `atT`/`hangS` only maps cleanly onto a single leg); `mv.jump` is dropped when `mv.via` is set, silently for now. 6 new tests in `tests/waypoints.test.ts` cover leg count, contiguous timing, exact position at each waypoint, and proportional duration allocation.

## Two small things added after Phase 3, ahead of Phase 4

Neither of these was in the original plan's Phase 3 scope, but both came from direct user feedback on the running app and were small/contained enough to do immediately rather than defer.

**Pose crossfading.** Poses used to snap instantly — `CapsuleHumanoid.setPose()` set every joint's THREE.js rotation directly with no interpolation, which read as janky/robotic during playback (the plan's own file tree names this as a planned feature, `poseBlend`, that never got built in Phase 1). Fixed properly: `PlayerVisual` gained an `update(dtSeconds)` method; `setPose()` now only records a target pose, and `update()` exponentially blends the skeleton's current joint angles toward it every frame (tau=0.08s, so it settles in ~0.15-0.25s) before applying to the THREE.js rotations. `SceneBridge.update()` fans this out to every player visual, called from `SceneCanvas`'s `onFrame` callback unconditionally — so it runs in both formation view and play mode, not just during playback. Couldn't get a clean empirical before/after in this session's browser automation (screenshots can't capture sub-200ms transitions, and — this is the same rAF-stalls-when-backgrounded quirk noted above — forcing repaints to sample joint rotation between tool calls hits `SceneRenderer`'s dt-cap of 0.25s per frame, which collapses the blend to ~1-2 samples instead of the ~15 a real focused tab would show). Verified instead by code review (it's a standard, well-understood exponential-decay pattern) plus confirming no regressions: no console errors, all 65 tests and `tsc`/`eslint` still pass, rendering still correct in both modes.

**A bench for the lineup panel.** `ui/panels/BenchPanel.tsx` + drag handlers added to `LineupPanel.tsx`'s slot rows, using plain HTML5 drag-and-drop (`ui/dragPlayer.ts` — a small shared payload type/helpers, no library needed). Drag a roster player from the bench onto a serve-order slot to start them; drag an on-court player back onto the bench to sit them; drag one on-court player onto another slot to swap them. The libero is deliberately left off the bench list — they're not a manual starter, they swap in automatically via `liberos[]` whenever their slot rotates back row (existing Phase 2 logic, untouched). No new store state: "who's on the bench" is just roster players not currently in `lineup.order`, so placing/benching is a single `setOrderSlot` call and the bench list updates for free. Verified all three interactions (bench→slot, slot→bench, slot→slot swap) by dispatching real `DragEvent`s with a `DataTransfer` via the console — this session's browser automation can't perform an actual OS-level drag gesture (`left_click_drag` moves the mouse but doesn't fire native HTML5 DnD events, confirmed by testing it first and seeing no effect), so this was the reliable way to exercise the actual event handlers rather than the mouse simulation. All three worked correctly and the 3D scene updated to match each time.

### What's *not* done yet in authoring (the honest gap)

- **Ball path is still read-only.** `bake.ts` deliberately doesn't touch `BallSegment.from/to` (documented scope decision from Phase 3) and `StepInspector` doesn't expose it either. A coach can move every player but can't yet redraw where the ball goes.

## What's next: Phase 5, serve-receive planning

Per the original plan: passer selector, serve origin/type/target picker, a responsibility-zone grid (multiplicatively-weighted Voronoi + marching squares), seam detection, and the uncovered-area time-margin heatmap the plan calls out as one of the most genuinely useful features — answering "can we handle a short serve to zone 2 in this rotation" better than a static diagram.
