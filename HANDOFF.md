## Load-bearing gotchas (from Phase 0/1, still relevant)

### The pose rotation sign convention (already fixed, don't re-break it)

`poseRig.ts` is authored so a positive `x` means "swing forward, toward the net" and a positive `z` means "swing outward, away from the midline": the intuitive way to read a pose table. Three.js's actual rotation math does the opposite for both axes on a hanging limb. This was empirically verified, not derived on paper (paper derivation got the sign wrong twice before empirical testing settled it), by directly reading a joint's world-space direction via its `matrixWorld` and checking it against the net/midline.

The fix lives in `CapsuleHumanoid`'s `applyJoints()`: it negates `x` and `z` for `spine`, `shoulderL/R`, and `hipL/R` before calling `rotation.set(...)`. The knees are the one joint that needed no correction. If you add new poses or new joints, verify the direction empirically (set a single joint, read `matrixWorld`, check world position against something you know) before trusting a hand-derived sign.

### Shoulder rotation compounds with spine lean

`shoulderL/R` are children of `spine`, so a spine forward lean adds to the shoulder's own forward swing, exactly like a real shoulder moving with a leaning torso. Each pose's authored shoulder angle is (desired total forward reach) minus (that pose's spine.x). If you tune a pose's spine lean, the shoulder angle needs to move with it. Hip angles don't need this treatment: the hip is a child of the pelvis, which never rotates.

### `preserveDrawingBuffer: true` is intentional

`SceneRenderer.ts` sets this on the WebGL context so `canvas.toDataURL()` works. This project uses it repeatedly to capture reference screenshots and the README's images, and `ui/exportRotationSheet.ts` (Phase 7) reads from it directly. It's cheap for this scene's complexity. Don't remove it as a "perf cleanup."

### Dev-only debug hooks exist

`import.meta.env.DEV`-gated globals: `window.__appStore`, `window.__lineupStore`, `window.__playbackStore`, `window.__playEditorStore`, `window.__serveReceiveStore`, `window.__sceneBridge`, `window.__sceneRenderer`. Never ship these in a prod build. Use them for anything that needs precise verification (reading exact joint rotations, driving state without racing a person clicking the UI, dispatching synthetic events) rather than guessing from a screenshot.

### Testing in an automated browser: render-loop stalls

When the browser pane isn't the foreground/visible surface, `requestAnimationFrame` can stall. Application state updates correctly and instantly, but the Three.js render loop stops advancing, so a screenshot can look pixel-identical to the previous one even though the underlying state genuinely changed. Taking a `computer` screenshot action forces a repaint; do it in the same batched call as the state change when you need to observe something reliably. This also means sub-200ms animations (like the pose crossfade) can't be cleanly sampled this way: `SceneRenderer`'s dt-cap (0.25s per frame) collapses a stalled-then-resumed blend into one or two big steps instead of the roughly 15 a real focused tab would show. Verify fast transitions by code review and regression tests instead of trying to screenshot them mid-flight.

### Stale Vite dep cache can look exactly like a real bug

If you hit a `ReferenceError` for an identifier that's clearly imported correctly in the source, especially after several rapid edits or new-file additions to a heavily imported file's dependency graph, don't trust it as a real bug before ruling out a stale cache. Kill the dev server, `rm -rf node_modules/.vite`, restart, and load the page in a **fresh tab** (an already-open tab can hold a stale module graph too). This wasted real time once before the cache turned out to be the actual cause.

### `left_click_drag` doesn't fire real HTML5 drag-and-drop

Confirmed by testing: the browser automation's mouse-drag simulation moves the cursor but doesn't trigger native `dragstart`/`dragover`/`drop` events. To exercise HTML5 DnD handlers (the lineup bench, e.g.) from this environment, dispatch real `DragEvent`s with a `DataTransfer` via `javascript_tool` instead. Plain pointer-event-based drag (no native DnD, see `PlayerDragController`) works fine with `left_click_drag`.

### `evaluate.ts`'s `findActiveSegment` must hold at the most recent segment during a gap, not "whichever segment is last in the array"

Fixed 2026-09-07 after a real user-visible bug (ball lags, teleports, snaps back). A segment array (`playerTracks[id]` or `ballTrack`) isn't guaranteed gapless: a ball segment can legitimately end before its own step does (contact is offset to start after the walk/approach finishes, see `commitContactAction`'s `contactAtS`), and a bare position-only step has no ball segment at all. The old fallback (`return segments[segments.length - 1]` whenever `t` didn't fall inside any interval) silently assumed no gaps existed, so a genuine gap made it grab the *last segment in the whole track*, evaluated at a clamped u, so a rendered object would flash to some future action's position before the real next segment kicked in and it snapped back. The fix holds at whichever already-started segment has the latest `startS` that's still `<= t` (the most recently completed one), falling back to `segments[0]` only when `t` precedes everything. If you ever touch this function again: a synthetic three-segment test with a real gap in the middle (see `tests/evaluate.test.ts`) is the fastest way to prove a change didn't reintroduce this.

### Scripting a drag test from this environment: two traps, both from the same session (2026-09-08)

First, **raycast against a player's actual mesh height, not their ground-level position pivot.** `PlayerVisual.root.position` sits at the character's feet (y=0) so floor-plane math works cleanly, but projecting *that exact point* to screen space and raycasting back through it can miss the mesh entirely from an angled camera: the visible silhouette's screen footprint is offset upward from where the feet actually project. Project a point at roughly chest height (`{...position, y: 1.0}`) instead when computing where to click/drag a player programmatically. The ball (a small sphere with real volume right at its own position) doesn't have this problem.

Second, **`setPointerCapture`/`releasePointerCapture` throw `NotFoundError` on a synthetic `PointerEvent`** dispatched via `element.dispatchEvent(new PointerEvent(...))`, because it was never associated with a real OS-level pointer session. Both `PlayerDragController` and the ball-drag controller that reuses it call `setPointerCapture` on `pointerdown`, and (as of the ninth session) so does `GuidedPlayController`. The exception is swallowed by the browser (event listeners don't propagate exceptions back to `dispatchEvent`'s caller) so the script appears to succeed while the drag silently never completes past that point. Check the console, not just the return value, if a scripted drag "does nothing." Two ways around it: use the `computer` tool's real `left_click_drag` (genuine trusted events, no capture issue, this is what the "`left_click_drag` doesn't fire real HTML5 drag-and-drop" note above is about, a different, DnD-specific limitation), or, for pixel-exact programmatic control, temporarily monkey-patch `Element.prototype.setPointerCapture`/`releasePointerCapture` to no-ops before dispatching synthetic events. That's a test-environment workaround only, never something to change in app code.

### The Browser pane's rendered viewport size can drift between calls

Discovered during the ninth session's verification. Projecting a 3D world position to 2D screen coordinates (to compute where to click a player) depends on `renderer.domElement.getBoundingClientRect()` at that exact moment, and that rect is not stable across separate tool calls in this environment: it changed from 1280x675 to 705x610 to 985x675 across a few seconds of testing in the same tab, with no explicit resize on the page's part. A coordinate computed in one `javascript_tool` call and then handed to a separate `computer` click call can land tens of pixels off target, or miss entirely, purely because the rect moved in between. Recompute the projection and the click target inside the same script, as close together as possible, rather than trusting a previously computed screen coordinate. For a real drag gesture (not a single click), synthetic `PointerEvent` dispatch from a single script (with the pointer-capture monkey-patch above) is more reliable here than a separate `computer` `left_click_drag` call, since the whole gesture's coordinates come from one consistent snapshot of the rect.

### Scripting a drop target: reproject at floor height, not at the chest-height point used to grab the player, and don't trust a dead drag's leftover visual state

Two more traps from the same round of `BenchDragController` verification, both easy to mistake for a real app bug:

First, the chest-height projection trick (`{...position, y: 1.0}`) exists to make a raycast actually *hit a player's mesh* on pickup. It does not carry over to picking a drop *destination*. If you want a drag to land at a specific world `(x, z)`, do not project a point at `y: 1.0` there and use that screen coordinate as the drop point: the controller's own drop-side raycast intersects the floor plane at `y: 0`, and under perspective a screen ray through a `y: 1.0` point lands somewhere else entirely on the `y: 0` plane, often meters away and sometimes on the wrong side of the net (`resolveDropTarget` then silently returns `null` and the whole drop is a no-op, which reads exactly like a broken drag). If a test needs a specific landing spot, pick the *screen point* by trial, or just accept whatever floor point a given screen delta produces and assert against that, rather than reverse-engineering the click from a target world position.

Second, `onDragMove` (in every drag controller) moves the actual Three.js mesh immediately, before any store write. If a scripted drag's `pointerup` never reaches a real commit (say, because the drop landed out of bounds and `onDrop` returned early), the mesh is left sitting at that last `onDragMove` position; nothing else in the app resets it until the next time something recomputes formation placement from the store. A later, unrelated script that reads `root.root.position` to compute a "current" position will pick up this stale, purely-visual leftover instead of the real anchor or override, producing confusing follow-on results that look like new bugs but are just uncommitted test residue. Reload the page (or otherwise force a fresh placement pass) between drag experiments rather than chaining them against the live mesh state.

### This environment's `computer` tool click/drag can miss the canvas entirely, even at coordinates read straight off a fresh screenshot

Confirmed directly during the tenth session, trying to verify a user-reported drag bug: after taking a screenshot, reading off what looked like an obviously-correct pixel for a clearly-visible player, and clicking there with the `computer` tool, nothing happened, no selection, no drag, repeatably, in a mode (Design Play) where a plain click should select a player. The same exact target, hit via a `PointerEvent` dispatched in-page with coordinates computed from `renderer.domElement.getBoundingClientRect()` and a real `THREE.Raycaster` in the same script, worked every time. DOM button clicks (`computer.left_click` on a real HTML button, or via a `find`-returned ref) were unaffected throughout, only canvas raycasting was off. This is on top of the already-documented viewport-rect drift: the two together mean a failed `computer`-tool click or drag against the 3D canvas in this environment is not strong evidence of an app bug by itself. Treat scripted `PointerEvent` dispatch (coordinates computed and used within one script) as the source of truth for canvas interactions here, and only trust `computer` tool clicks/drags on canvas content when they succeed, not when they fail.

**A note on the block shadow's geometry, since it's easy to get backwards:** the shadow lands on the *defending* team's floor, not the attacker's own side. `computeBlockShadow`'s rays start at the attacker's contact point (on their own side, near the net) and are cast *through* the block's top edge (at the net, y>0), continuing on to y=0, which by simple ray continuation lands past the net on the opponent's side. The tip-coverage region is separately computed at a fixed shallow depth on the *defending* side near the 3m line (`deriveMatchupState.ts`'s `tipTargetWorld`). It is deliberately **not** centered on the attacker's own contact point, which was the first (wrong) implementation caught during browser verification: the ring rendered on the wrong side of the net until fixed.

**Guided authoring, round 6 (2026-09-07, same day), ball motion, jump height, done-color removed, default theme, replay.**

- **Uniform-speed ball flight.** `ballHeightAt` (`core/play/ballFlight.ts`) used to ease like a real projectile, a quadratic on each side of the apex, so it lingered near the top and accelerated toward either end. **GuidedPlayController drag hardening (2026-09-08, tenth session).** A follow-up report said "Move players" worked in Formation mode but not in Design Play. Direct `PointerEvent` dispatch with real, freshly-computed coordinates showed the gating logic itself already worked correctly in both places (confirmed a full drag committed a real movement when the toggle was on, and that the same gesture left the player untouched and registered as a click when it was off), so the fix here targets robustness against a real mouse rather than a broken gate:

- `GuidedPlayController` used to wait until a drag crossed its `DRAG_THRESHOLD_PX` (6px) click-vs-drag threshold before calling `setOrbitEnabled(false)`/`setPointerCapture`, unlike `PlayerDragController` and `BenchDragController`, which do both immediately on pointerdown, the moment a player is hit. That gap meant a real mouse's first few pixels of movement could let `OrbitControls` start rotating the camera, or let the pointer drift off the canvas without capture, before the controller's own drag logic ever engaged. Restructured so a new `isPotentialDrag` flag (true whenever pointerdown hits a player and `isDragEnabled()` is true) drives the immediate orbit-disable and pointer-capture, while the actual click-vs-drag *decision* (and so whether `onSelectPlayer` or `onDragMove`/`onDragEnd` fires) still only resolves once the threshold is crossed, exactly as before.
- All three player-drag controllers (`PlayerDragController`, `BenchDragController`, `GuidedPlayController`) now call `e.preventDefault()` on a successful pointerdown hit, so the browser's own native drag-to-select-text or drag-an-element gesture can never start on top of a real mouse press over the canvas and interrupt the pointermove/pointerup sequence mid-gesture.

**Flagged honestly, not swept under the rug:** this session's own browser automation could not reproduce the exact reported failure. **The real Design Play drag bug, attack jump timing, ball path preview (fresh session).** The user reported the same "can't move players while designing a play" complaint again after the tenth session's hardening pass, plus two unrelated asks: make the spiker genuinely airborne at contact with a realistic hang time, and show the ball's actual flight path when authoring an attack.

- **The actual drag bug.** Reproduced this time, with a repaint-forcing methodology (see the new gotcha below on why the previous session's testing missed it): `commitPositionAction` (`app/guidedAuthoring.ts`) always appended a repositioning drag's movement to `play.steps[play.steps.length - 1]`, the *last* step, no matter which step the playhead was currently showing. On a single-step play this is invisible (the last step is the only step), which is exactly the case both this session's and the previous session's quick manual checks happened to use. On a real multi-step play, dragging a player while reviewing an earlier step wrote the movement into a step that wasn't on screen; the drag looked like it worked (the live `onDragMove` feedback moves the actual mesh immediately) right up until the next real repaint recomputed the current step's own hold position and the player snapped back to their old spot, reading as "dragging doesn't work." Fixed by threading the step under the current playhead through explicitly: new `stepIdAtTime(play, t)` (`app/guidedAuthoring.ts`) walks each step's `duration` cumulatively to find which one contains `t`, and `commitPositionAction` takes an optional `stepId` that, when given, targets that step instead of the last one (the click-based action-menu flow in `GuidedAuthorPanel.tsx` still omits it, keeping its own "append forward" behavior, since that flow is about building the play forward in time, not editing a specific already-authored moment). `SceneCanvas.tsx`'s `onDragEnd` now passes `stepIdAtTime(p, usePlaybackStore.getState().t)`. Also fixed while in there: repeatedly dragging the same player within the same step used to stack a second, conflicting movement instead of replacing the first; `commitPositionAction` now filters out any existing movement for that player in the target step before adding the new one. Verified directly: built a real two-step play, scrubbed to the first step, dragged a player, and confirmed (after a forced repaint, not just reading the store) the change was visible at that step's own time and gone at the other step's, in both directions.
- **Attack jump timing.** `scaledJump()` (`app/guidedAuthoring.ts`) computes `atT` (the jump's peak time) so contact happens at the very *end* of the arc, which per `jumpOffsetY`'s own parabola (`core/play/playerMotion.ts`, `4 * heightM * u * (1-u)`) is `u=1`, the landing point, offset back to zero. So despite a real jump animation existing, the attacker was always exactly grounded at the instant of contact, no matter how high `heightM` was set. The docstring even claimed the opposite ("contact happens near the top of the jump"), which is what made this easy to miss before. Fixed by moving contact to `u=0.85` instead of `u=1.0` (`CONTACT_ARC_U`): still descending, not at the literal peak, but at 85% of the arc the offset is `4*0.85*0.15 = 51%` of peak height, clearly airborne, verified empirically at 0.51m elevation for the default 1.0m jump height. The small remaining drop (from 51% down to 0%) gets absorbed as a snap when the next step's plain hold takes over, since there's no matching "landing" jump segment defined for the following step; a real cross-step descent would need one, and wasn't built here, it's not needed once contact itself reads as airborne. Also bumped `GUIDED_CONTACT_DEFAULTS.attack.jump.hangS` from 0.3 to 0.6 (a realistic full hang time), which the existing (unchanged) `scaledJump` cap already scales down for a faster set tempo, so a quick 1-tempo still gets a short, snappy hang while a high ball gets the full 0.6s, and applied `scaledJump` to the rare first-touch fallback path (an attack with nothing preceding it) too, which previously used the raw, unscaled default and could have produced a jump longer than its own movement.
- **Ball path preview.** New `render/overlays/BallPathLine.ts`: samples `core/play/ballFlight.ts`'s own `ballPositionAt()` (the exact function that positions the ball during real playback) at 24 points per ball segment and draws a dashed `THREE.Line` through them, reusing `theme.ball.trailColor` rather than adding a new theme token. `SceneBridge.setBallPath(arcs)` follows the same create/dispose pattern as `setApproachLane`. Wired into `SceneCanvas.tsx`'s existing schedule-recompile effect (the same one that already had the snap-back bug fix above), so it updates automatically whenever the play changes, covering every ball segment in the play at once, serve through attack, not just the most recent one. Deliberately dashed and semi-transparent so it reads as "the planned route" and is never confused with `BallTrail`'s existing solid fading trail, which still only appears behind the ball while it's actually moving during playback.

### Verifying a fix by reading the store isn't enough when the bug is about what gets *rendered*

The tenth session's drag investigation read `play.steps` after a scripted drag and saw a real movement had been added, concluded the mechanism worked, and moved on. It had, technically, in the single-step play used for that check. The actual bug (movements landing in the wrong step on a multi-step play) only shows up in the *rendered* position at a specific `t`, and even then, per the already-documented render-loop-stall gotcha, only after a real repaint, not just a `javascript_exec` readback. The fix this session used the same trap once already (see the "leftover visual state" gotcha above) before correcting course with `computer` screenshots between every `setT` call and every readback. If a bug report is specifically about something looking wrong on screen, verify the actual rendered state after a forced repaint, not just the underlying store data, before concluding a fix worked or a mechanism was never broken.

Tune `serveSpeedMps`/`passerSpeedMps`/`serveApexM` in `ServeReceivePanel.tsx` and `SceneCanvas.tsx`'s serve-receive effect if the balance feels off.
