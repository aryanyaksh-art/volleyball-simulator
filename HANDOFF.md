## Load-bearing gotchas (from Phase 0/1, still relevant)

### The pose rotation sign convention (already fixed, don't re-break it)

`poseRig.ts` is authored so a positive `x` means "swing forward, toward the net" and a positive `z` means "swing outward, away from the midline": the intuitive way to read a pose table. Three.js's actual rotation math does the opposite for both axes on a hanging limb. This was empirically verified, not derived on paper (paper derivation got the sign wrong twice before empirical testing settled it), by directly reading a joint's world-space direction via its `matrixWorld` and checking it against the net/midline.

The fix lives in `CapsuleHumanoid`'s `applyJoints()`: it negates `x` and `z` for `spine`, `shoulderL/R`, and `hipL/R` before calling `rotation.set(...)`. The knees are the one joint that needed no correction. If you add new poses or new joints, verify the direction empirically (set a single joint, read `matrixWorld`, check world position against something you know) before trusting a hand-derived sign.

### Shoulder rotation compounds with spine lean

`shoulderL/R` are children of `spine`, so a spine forward lean adds to the shoulder's own forward swing, exactly like a real shoulder moving with a leaning torso. Each pose's authored shoulder angle is (desired total forward reach) minus (that pose's spine.x). If you tune a pose's spine lean, the shoulder angle needs to move with it. Hip angles don't need this treatment: the hip is a child of the pelvis, which never rotates.

### `preserveDrawingBuffer: true` is intentional

`SceneRenderer.ts` sets this on the WebGL context so `canvas.toDataURL()` works. It's used repeatedly this project to capture reference screenshots and the README's images, and it's what `ui/exportRotationSheet.ts` (Phase 7) reads from directly. Cheap for this scene's complexity. Don't remove it as a "perf cleanup."

### Dev-only debug hooks exist

`import.meta.env.DEV`-gated globals: `window.__appStore`, `window.__lineupStore`, `window.__playbackStore`, `window.__playEditorStore`, `window.__serveReceiveStore`, `window.__sceneBridge`, `window.__sceneRenderer`. Never ship in a prod build. Use these for anything that needs precise verification (reading exact joint rotations, driving state without racing a person clicking the UI, dispatching synthetic events) rather than guessing from a screenshot.

### Testing in an automated browser: render-loop stalls

When the browser pane isn't the foreground/visible surface, `requestAnimationFrame` can stall. Application state updates correctly and instantly, but the Three.js render loop stops advancing, so a screenshot can look pixel-identical to the previous one even though the underlying state genuinely changed. Taking a `computer` screenshot action forces a repaint; do it in the same batched call as the state change when you need to observe something reliably. This also means sub-200ms animations (like the pose crossfade) can't be cleanly sampled this way: `SceneRenderer`'s dt-cap (0.25s per frame) collapses a stalled-then-resumed blend into 1-2 big steps instead of the ~15 a real focused tab would show. Verify fast transitions by code review and regression tests instead of trying to screenshot them mid-flight.

### Stale Vite dep cache can look exactly like a real bug

If you hit a `ReferenceError` for an identifier that's clearly imported correctly in the source, especially after several rapid edits or new-file additions to a heavily-imported file's dependency graph, don't trust it as a real bug before ruling out a stale cache. Kill the dev server, `rm -rf node_modules/.vite`, restart, and load the page in a **fresh tab** (an already-open tab can hold a stale module graph too). This wasted real time once before the cache turned out to be the actual cause.

### `left_click_drag` doesn't fire real HTML5 drag-and-drop

Confirmed by testing: the browser automation's mouse-drag simulation moves the cursor but doesn't trigger native `dragstart`/`dragover`/`drop` events. To exercise HTML5 DnD handlers (the lineup bench, e.g.) from this environment, dispatch real `DragEvent`s with a `DataTransfer` via `javascript_tool` instead. Plain pointer-event-based drag (no native DnD, see `PlayerDragController`) works fine with `left_click_drag`.

### `evaluate.ts`'s `findActiveSegment` must hold at the most recent segment during a gap, not "whichever segment is last in the array"

Fixed 2026-09-07 after a real user-visible bug (ball lags, teleports, snaps back). A segment array (`playerTracks[id]` or `ballTrack`) isn't guaranteed gapless — a ball segment can legitimately end before its own step does (contact is offset to start after the walk/approach finishes; see `commitContactAction`'s `contactAtS`), and a bare position-only step has no ball segment at all. The old fallback (`return segments[segments.length - 1]` whenever `t` didn't fall inside any interval) silently assumed no gaps existed, so a genuine gap made it grab the *last segment in the whole track* — evaluated at a clamped u, so a rendered object would flash to some future action's position before the real next segment kicked in and it snapped back. The fix holds at whichever already-started segment has the latest `startS` that's still `<= t` (i.e., the most recently completed one), falling back to `segments[0]` only when `t` precedes everything. If you ever touch this function again: a synthetic three-segment test with a real gap in the middle (see `tests/evaluate.test.ts`) is the fastest way to prove a change didn't reintroduce this.

## What's built

**Phase 0-1, scaffold, court, camera, silhouettes.** Vite + React 19 + TypeScript strict, Vitest for the domain layer, ESLint boundary rule (`src/core` cannot import `three`/`react`/anything from `render`/`ui`). Court geometry and the team-local/world coordinate transform (`core/court/coordinates.ts`: get familiar with `toLocal`/`toWorld` before touching anything rotation-related). Free-orbit camera plus 5 tweened presets. A net with a real ~1m panel and a visible gap above the floor (not a floor-to-ceiling rectangle), padded posts, banded edges, dashed antennas. Humanoid silhouettes (tapered torso via `LatheGeometry`, hip girdle, hands, feet) with all 16 poses, now **pose-crossfaded** (`PlayerVisual.update(dt)` exponentially blends toward whatever pose was last requested, tau≈0.08s: poses no longer snap instantly). 3 theme presets, zero color literals outside `Theme`.

**Phase 2, rotation engine.** `core/roster/`, `core/lineup/` (types, rotation math verified for all 36 rotation×zone combos, `breakdown()` derives on-court zone/row/server/functional-setter per rotation with automatic libero substitution), `core/rules/overlap.ts` (`checkAlignment()`: the exact 7 adjacent-pair comparisons, server-exempt, margins for every pair not just violations; `nudgeToLegal()` iteratively fixes violations, implemented and tested but not wired to any UI button yet). UI: `RosterPanel`/`LineupPanel`/`RotationWheel`/`ValidationPanel`/`FormationPanel`/`BenchPanel`, backed by `useLineupStore`. `LineupPanel` supports drag-and-drop between a bench and the 6 serve-order slots (plain HTML5 DnD, `ui/dragPlayer.ts`). `FormationPanel` is a manual per-zone position override: the only way to actually push a formation illegal in the running app (Phase 3+ real position data doesn't exist as an editable target here, since a play's own formation now serves that role once you're authoring a play). A 3D `ViolationOverlay` connector line draws between offending players live. No camera auto-focus on a violation yet.

**Phase 3, play model plus deterministic playback.** `core/play/types.ts` (symbolic `PlayerRef`/`PositionRef` refs), `compile.ts` (flattens `Play.steps` into absolute-time tracks, "hold" segments for anyone not given a movement, supports `Movement.via` waypoints split into proportional straight-line legs), `evaluate.ts` (pure function of `t`, no `dt` accumulation, verified deterministic by sampling 200 values of `t` twice and asserting identical results), `ballFlight.ts` (exact closed-form parabola, exact at both endpoints and the apex, supports an asymmetric `apexU` for a spike's near-contact peak), `diagnostics.ts` (`diagnosePlay()` surfaces the two checks the plan calls highest-value: `checkSpeedCap`, a move faster than a human can physically make, and `checkBallFlight`, which catches net clips, antenna misses, and landing out). Render wiring: `BallVisual`, `SceneRenderer.start()` takes a per-frame callback (the one seam playback ticks through: React never drives the render loop). 3 demo plays in `fixtures/demoPlays.ts` (serve/pass/set/attack; a pipe attack for the rotation where the setter's front row; a 1st-tempo quick middle), selectable via `TransportBar`. `core/play/bake.ts` resolves any play's symbolic refs down to concrete `{kind:'slot'}`/`{kind:'local'}` refs (including ball segments): this is what makes a play safely editable in Phase 4, proven behavior-preserving by compiling a play before and after baking and asserting identical tracks.

**Phase 4, play authoring.** `usePlayEditorStore` (the play being edited, `selectedStepId`, undo/redo history capped at 50 snapshots, `saveCurrentPlay()` to `localStorage`). `TimelineEditor` (step chips, reorder/resize/rename/add/remove) plus `StepInspector` (per-step: every on-court player either "holds position" with a one-click "+ Move," or editable lat/depth/mode/pose; the ball's kind/apex/duration/from/to are editable too). `PlayerDragController`, the plan's primary authoring gesture: grab a player in the 3D view, drag across the floor plane (temporarily disables `OrbitControls`), snaps to 0.1m, Shift for free placement; only `pointerup` commits, via `moveOrAddMovement`. Editing a built-in demo forks it into a new saved play on first save rather than colliding with the demo's own id in the play picker.

**Phase 5, serve-receive planning.** `core/tactics/serveReceive.ts`: `assignResponsibility()` is a multiplicatively-weighted Voronoi assignment (a libero/primary passer's higher weight extends their range past a nearer, lower-weight teammate); `isSeam` triggers when the top two are within 0.4m. `solveTimeToHeight()` finds where a serve's parabola descends through a playable contact height (not floor contact) via bisection on `ballHeightAt()`. `analyzeServeReceive()` rasterizes the receiving half plus free zone and combines both into a per-cell margin (flight time minus the fastest passer's reach time), classified safe/tight/uncovered. `CoverageHeatmap.ts` bakes the whole grid into one `BufferGeometry` (one draw call, not one mesh per cell). `ServeReceivePanel` plus `useServeReceiveStore`: check passers, set weights, pick a serve origin zone, watch the heatmap and summary counts update live. Verified from a top-down camera with a real 3-passer system: the result is legible (green rings around passers, red in the seams/corners), not a uniform wash.

**Phase 6, attack/defense matchups.** `core/tactics/attack.ts` (`computeApproachLane()`: per-role takeoff/run-up geometry for OH/MB/RS/pipe, a simplified single-segment approach rather than real footwork; `computeBlockFeasibility()`: reaction time plus lateral travel at shuffle/crossover speed vs. the set's tempo, producing the plan's "MB cannot reach the pin" message shape; `SET_TEMPO_S` table; zone/role convention `ZONE_TO_ROLE`/`ATTACK_CONTACT_BY_ZONE`), `core/tactics/block.ts` (`computeBlockShadow()`: ray-cast quadrilateral from the hitter's contact point over the block's top edge onto the floor, clipped to the court by coordinate clamping rather than full polygon clipping; `checkDefendersInShadow()` via ray-casting point-in-polygon; `checkOpenAngle()` and `checkTipCoverage()`: reach-margin checks, cone/region modeled simply as distance-to-midpoint/circle rather than full geometric coverage), `core/tactics/defense.ts`/`defense.presets.ts` (`defensiveBase()`: perimeter/rotation/man-up/six-back base positions keyed by attack zone, a coaching-tool sketch rather than a full read-and-react system). `app/deriveMatchupState.ts` is the SceneCanvas/panel coupling point (mirrors `deriveRotationState.ts`'s role). It's also what keeps the defending side's rendered positions and the shadow/tip math consistent: both read through the same `defensiveBase()`-overridden `effectivePosition()`, so switching "Defense" in the panel visibly moves players **and** changes the feasibility numbers together. `MatchupPanel`/`MatchupSidebar` plus `useMatchupStore`; render overlays `ApproachLanes.ts` (line plus end markers) and `BlockShadow.ts` (shadow quad plus tip-coverage ring), wired into `SceneBridge.setApproachLane()`/`setMatchupShadow()`. Verified live in the browser: switching attack zone, set call, block scheme, and defensive system all visibly update the 3D overlays and the panel's numbers together (screenshotted in a fresh tab with an empty console, no React warnings, no failed module reloads).

**A note on the block shadow's geometry, since it's easy to get backwards:** the shadow lands on the *defending* team's floor, not the attacker's own side. `computeBlockShadow`'s rays start at the attacker's contact point (on their own side, near the net) and are cast *through* the block's top edge (at the net, y>0), continuing on to y=0, which by simple ray continuation lands past the net on the opponent's side. The tip-coverage region is separately computed at a fixed shallow depth on the *defending* side near the 3m line (`deriveMatchupState.ts`'s `tipTargetWorld`). It is deliberately **not** centered on the attacker's own contact point, which was the first (wrong) implementation caught during browser verification: the ring rendered on the wrong side of the net until fixed.

**Post-v1, simple mode and guided authoring.** Design spec at `docs/superpowers/specs/2026-09-07-simple-mode-and-guided-authoring-design.md`, implementation plan at `docs/superpowers/plans/2026-09-07-simple-mode-and-guided-authoring.md` (both worth reading before touching this area, especially the plan's task-by-task file list). Four pieces:

- **Advanced/Simple toggle.** `useAppStore.authorAdvancedMode` (default `false`), a floating `.advanced-toggle` chip top-right of the scene in author mode. `App.tsx` renders `AuthorSidebar` (the old timeline/step-inspector) only when it's on, `GuidedAuthorPanel` only when it's off. - **Libero color.** `Theme.liberoColor`, one value per theme, applied in `buildSceneState()` (formation mode, via the already-available `p.isLibero`) and in the play/author playback loop, where `isLibero` isn't part of `WorldState` and has to be recomputed: a `liberoOnCourtIdsRef` is rebuilt alongside the compiled schedule, from `breakdown(...).onCourt`, using **the play's own `scenario.rotations`**, not the live global lineup rotation (a play can be scoped to a different rotation than whatever's currently selected in formation mode).

Formation mode only; gated off in author/play mode the same way the existing drag controllers already are.

Wired for position actions (block/dig/move) as well as contact actions; the height/apex picker itself now only shows for genuine contact actions, since it was previously rendering a meaningless "apex" slider for a plain positioning move.
- **Players walk to the ball instead of standing still.** Contact actions (serve/pass/set/attack/tip) used to give the acting player a self-referencing `{kind:'atPlayer', ..., contact:'feet'}` hold — no real movement, ever. Now: a serve always moves to `SERVE_READY_TARGET` (centered, behind the endline, past `DEFAULT_COURT_SPEC.halfLengthM`), and every other contact action resolves `resolveIncomingArrival()` — the *previous* step's ball landing spot (a zone anchor for a set, the resolved local position otherwise), converted into the acting player's own local frame via a `toWorld`/`toLocal` round trip since the two sides don't share a coordinate origin — and walks there. Falls back to the old hold only when there's nothing incoming yet (the play's first step). **The ball's own `from` had to move too**, and this is the part worth re-deriving carefully if it ever looks wrong again: `compile.ts` resolves an `atPlayer` ref against the snapshot from the *start* of the step, before that step's own movement has applied, so leaving `ball.from` as `atPlayer` while giving the player a real same-step movement would make the ball depart from their *old* position while they visibly walk somewhere else. `commitContactAction` now builds `ball.from` as an explicit `{kind:'local', ...}` at the same walk-to position (with the right contact height — `CONTACT_HEIGHT_BY_ACTION`, mirroring `refs.ts`'s `CONTACT_HEIGHT_M`) whenever there's somewhere to walk to, and only falls back to `atPlayer` in the same no-movement first-step case.
- **A step now stretches to cover its own movement — and contact waits for the walk to finish (revised again in round 3, see below).** A step's `duration` used to come from the ball segment alone (`ball.duration ?? 1`), which was always safe when movements were short self-referencing holds. Once a contact action can need a multi-second walk (a serve to the far service line can be ~9-11m), that broke. The *original* fix here took `Math.max(ball.duration, movement.duration)`, treating the walk and the flight as running in parallel — which turned out to be wrong (the ball would take off mid-walk); round 3 replaced it with sequential composition. `commitPositionAction`'s "append to the currently-open step" path still uses `Math.max(existing step duration, new movement duration)`, which is correct there (a different player's movement being folded into an existing step, not something that needs to happen *after* that step's own ball contact). The serve default's `movementDurationS` was also bumped from 0.35s (fine for a hold, hopeless for an actual walk) to 2.2s in `guidedDefaults.ts`.
- **Bench section in Design Play.** Formation mode's on-court 3D bench (`BenchDragController`) was flagged user-reported-broken in the previous commit. Investigating it this session found the underlying pointer-drag mechanism actually works correctly end-to-end (confirmed by dispatching real `PointerEvent`s at the mesh's exact projected screen position and watching `lineup.order` update) — the real problem is discoverability: a bench player is a small, dim, `BENCH_SCALE`-shrunk silhouette standing 1.5m past the free zone, often entirely outside the default camera framing, so a real user can't see it well enough to grab it, let alone hit the exact pixel. Rather than chase that 3D interaction into a second mode, guided authoring got a plain sidebar list instead (`GuidedAuthorPanel`'s new "Bench" section, one chip per benched player per side, both sides shown since guided mode has no side selector): click a bench chip (`useGuidedAuthorStore.pendingBenchSwap`), then click the on-court player they're replacing (wired into `GuidedPlayController`'s `onSelectPlayer` in `SceneCanvas.tsx`, ahead of the normal action-assignment selection), and the swap applies via the same `setOrderSlot` every other bench interaction already uses. Mutually exclusive with the action-assignment flow in both directions. The formation-mode 3D bench's discoverability problem itself is still unfixed — see "Honest gaps" below.

**Roster editing (2026-09-07, same session).** Checking the live bench panel surfaced that it had never actually been tested with real bench depth: the demo roster is a fixed 6 starters + 1 libero, and `RosterPanel.tsx` had no way to add anyone, so every bench UI in the app (this session's two included) had nothing to show. `useLineupStore` gained `addPlayer(side, playerWithoutId)` (generates the id — `${side}-${randomUUID().slice(0,8)}`, never accepts a caller-provided one) and `removePlayer(side, playerId)`, which clears that player out of `lineup.order` (mapped to `null`, not spliced — slot *indices* matter elsewhere) and out of `lineup.liberos` before dropping them from the roster, since neither can be left pointing at someone who no longer exists. `RosterPanel` gained a per-row Remove button and an inline add-player form (name/number/role/handedness) that defaults the number field to the lowest unused one and rejects a duplicate. Verified live: added "#8 Backup OH" via the form, confirmed it showed up in both `BenchPanel` and the new Design Play bench section, then used the latter to swap them onto the court.

**Guided authoring, round 3 (2026-09-07, same day) — the ball-motion bug, plus deselect/drag/emoji.** User-reported: playback showed the ball lagging at its landing spot, teleporting somewhere else, then snapping back before the real next motion played, and a serve+pass sequence looked directionally wrong. Two compounding causes, both from round 2's walk-to-the-ball change:

- `evaluate.ts`'s `findActiveSegment` fallback bug — see the new "Load-bearing gotchas" entry above for the full mechanics. This is the general fix; it isn't guided-authoring-specific and applies to player tracks too, just less visibly since `compile.ts` still guarantees gapless player coverage per step.
- Sequential contact timing. A contact action's movement (the walk) and its ball segment both started at the step's `t=0` — parallel, not sequential — so the ball could fly while the player was still mid-approach, then sit at the landing spot once its own short flight duration elapsed while the walk kept going. `commitContactAction` now sets `ball.startOffset = movement.duration` (`contactAtS`) and the step's duration to `contactAtS + ball.duration` (sum, not `Math.max` — see the revised "A step now stretches..." entry above). Verified live: sampled ball world position across a full serve+pass sequence at points spanning both segment boundaries and the inter-segment gap — smooth throughout, ball correctly holds at the floor-level landing spot while the passer walks over, only rising to contact height once they arrive.

Also landed in the same round, all independent of the above:

- **Deselect.** Clicking the already-selected player again deselects them (only before an action's chosen); clicking open floor with a player selected but no action chosen does the same; the action-chosen-but-no-target-yet stage of `GuidedAuthorPanel` gained a Cancel button it was previously missing (it only appeared once a target existed).
- **Drag anywhere on the court.** `GuidedPlayController` used to treat any real pointer movement as camera orbit and ignore it — clicking was the only guided-mode interaction. It now raycasts for a player hit on `pointerdown` and only resolves to a click once release happens with no meaningful movement in between; a real drag disables `OrbitControls`, gives live visual feedback (`bridge.setPlayerPosition`), and commits via `commitPositionAction({action:'move', ...})` on release — the same function the click-based "move" chip already calls, so dragging is a shortcut into that same path, not a separate one. Dragging a player who's mid-flow in the click-based flow cancels that flow first.
- **No more emoji.** Every button/label across the app (Design play, Serve-receive, Matchups, Save play, Present, Export sheet, Advanced, Undo/Redo, etc.) had a leading pictographic character. All replaced with plain text; a few icon-only buttons in narrow table cells/timeline chips now use plain ASCII (`<`, `>`, `x`) instead of Unicode arrow/cross glyphs.

**Guided authoring, round 4 (2026-09-07, same day) — concurrent movement, the selected-player color, net height, and on-screen benches.** Four more pieces of live feedback, landed together:

- **The bottom `ControlBar` (theme/camera/pose-preview) joined the Advanced toggle.** Gated behind `authorAdvancedMode` in `App.tsx` instead of always rendering, same pattern as the rest of the app.
- **`guidedSelectedColor`.** There was never a color tied to selection — what read as a "selected" highlight was always `guidedDoneColor`, so deselecting a player who already had an action anywhere in the play changed nothing visually. Added a dedicated theme color (magenta, one per preset) with top priority in `SceneCanvas.tsx`'s per-frame coloring, above libero and done.
- **Net-height reference line.** `SideHeightPicker.tsx` draws a dashed line at `DEFAULT_COURT_SPEC.netHeightM` (the same constant the actual net geometry uses), labeled "net" — a raw meter value doesn't mean much on its own, but "does this clear the net" is immediate.
- **Concurrent movement — the big one.** User-reported: players stood frozen until their own step began, even when the ball was already headed their way during the *previous* step, and never moved two-at-once (a setter wouldn't start moving until the libero's whole pass had finished). An attacker also waited for a set to land before jumping, instead of jumping to meet it.

  `commitContactAction`'s non-serve path was redesigned: instead of a movement inside its own new step, a reacting player's approach is now injected as an *additional* movement into the **previous** step (the one whose ball is incoming), with `startOffset`/`duration` copied from that step's own ball segment — so the approach starts exactly when the ball is launched and ends exactly when it lands, no earlier and no later. The new step itself needs no movement of its own for the actor anymore (they already arrived), so its ball resolves via a plain `atPlayer` reference immediately at `t=0`. This is what lets several players move within one step's time range: a step's `movements` array now typically holds nothing for its own actor (that's in `ball.from`) but *does* hold whoever's about to react to it next, injected there by that next action's own commit. `scaledJump` re-times an attack's jump (peak near the end of the approach) since the fixed `atT`/`hangS` in `GUIDED_CONTACT_DEFAULTS.attack` were tuned for the old, always-short hold-movement duration and would otherwise finish jumping long before a set with a real flight time arrives. Serve is unchanged — nothing precedes it to react to.

  This forced two real changes to Edit/Remove, since a step's own actor is no longer reliably `step.movements[0]`: `contactActorOf(step)` finds them via `ball.from`'s atPlayer reference (falling back to the old single-movement shape for the play's first-ever touch), and `removeGuidedStep` now also strips that actor out of the *previous* step's movements if a reaction was injected there, so removing a step doesn't leave someone walking toward a now-actionless target. Edit is now restricted to the play's **last** step only — `spliceGuidedStepReplacement` (which re-inserted at an arbitrary earlier index) is gone; re-authoring a non-last step correctly needs to know which later step to reinsert before, which this simpler "remove old reaction, recommit, it naturally lands in the right place" approach doesn't attempt. Verified live: built a full serve/pass/set/attack sequence and read the resulting `PlayStep`s directly (the pass step's movements array held the *setter's* approach, not the passer's; the set step's held the *attacker's*, jump included, `atT` past the movement's own midpoint), then sampled world positions mid-flight and watched the attacker visibly airborne while the set ball was still in the air.
- **On-screen benches flanking the court.** Two panels overlaid directly on `.scene-viewport` (top-left for side B, bottom-left for side A — positioned per a user-provided screenshot), in both formation and Design Play, instead of a bench only reachable through a sidebar list. Real drag-and-drop this time: `ui/CourtBenchOverlay.tsx`'s chip captures the pointer on `pointerdown` (`setPointerCapture`), so `pointerup` still fires on that same chip even once the cursor is over the WebGL canvas — capture redirects every subsequent pointer event to the capturing element regardless of what's actually under the cursor. To resolve what's under that screen position without reaching into `SceneCanvas`'s internal renderer/camera refs, `useAppStore` gained `resolveCourtDropTarget`, a raycasting closure `SceneCanvas` registers on mount (reusing `BenchDragController`'s existing `resolveDropTarget`) and clears on unmount. Each bench overlay also has a quick "+" add-a-sub and a per-chip "x" remove, both just calling the same `addPlayer`/`removePlayer` `RosterPanel` already exposes. **Testing note:** the browser automation's own drag simulation (`left_click_drag`) didn't reproduce a real pointer-capture sequence faithfully here — verification instead dispatched synthetic `PointerEvent`s directly, which worked immediately and confirmed the app code itself is correct. Not done: benched players still render standing (a real sitting pose needs new joint authoring in `render/players/poseRig.ts`, which the existing pose-sign-convention gotcha above says needs empirical verification, not a rushed guess), and dragging an on-court player back onto an overlay to bench them isn't wired — only bench-to-court.

## Honest gaps, by area

**Rotation/lineup:** no camera auto-focus on a violation; `nudgeToLegal()` unused by any UI button.

**Play model:** `Movement.facing = {atPlayer: ...}` is typed but `compile.ts` only honors `{rad: ...}` (facing-toward-a-player silently holds the previous angle: never fixed because verifying the yaw convention needed the same kind of empirical check as the pose-sign issue above, and there wasn't time). No `TrajectoryLine`/`MotionTrail`: the ball is a plain sphere with no visual flight path. No persistence beyond raw JSON in `localStorage`: no zod schema, no versioned migration.

**Authoring:** no 3D drag for the ball (form fields only); no ghost-silhouette/dashed-path preview while dragging; no Alt-modifier snap-to-zone-anchor (only the 0.1m grid snap and Shift-for-free exist); `setStepDuration`'s minimum is a hardcoded 0.05s floor with no validation against its own ball segment's duration; no "extend this step" one-click apply from a speed-cap diagnostic (the suggested duration is computed and shown, just not clickable); no play library view (the picker dropdown shows one entry per saved play, no dedicated manage/browse panel).

**Serve-receive:** no serve type/target picker or click-to-place target, only a serve *origin* zone; the analysis covers the whole grid for that origin, not one aimed serve. No marching-squares contour outlines (flat per-cell color). Serve profile (speed/apex/contact height) is hardcoded, not derived from a serve-type choice: see the modeling-choice note below. `ServeReceivePanel.tsx` and `SceneCanvas.tsx` each independently build the same `Passer[]` list and call `analyzeServeReceive()`. It works and is verified consistent, but it's real duplication a shared hook should replace. No formation presets (W, 3-passer, 2-passer, stack-left/right) or auto-nudge-to-legal.

**Attack/defense matchups:** `checkOpenAngle()`/`OpenCone` (line/angle/seam) exist in `core/tactics/block.ts`, tested, but nothing builds a cone from real geometry or renders one yet. The plan's own description of these cones is the vaguest part of the spec, so this was deliberately left tested-but-unwired rather than force-fitting an under-specified feature (same pattern as `nudgeToLegal()` in Phase 2). Block scheme only changes blocker count (1 for spread/bunch-read, 2 for bunch-commit, 0 for release) and total block width, not real positioning differences between spread/bunch-read (they're visually and numerically identical today; the panel does still label the scheme). Defensive base positions don't respect `positionOverrides`, unlike the rest of the app. No UI to pick which hitter/blocker on the roster is actually attacking/blocking: it's zone-based, not player-based, so it doesn't reflect a specific player's real approach jump reach.

**Polish/deploy:** the Wake Lock API isn't universally supported (notably older Safari). Presentation mode still works there, it just won't keep the screen awake, and there's no in-app indicator telling the coach whether the lock was actually granted. No PWA/offline manifest: explicitly a stretch goal in the plan, not required for v1. No zod schema/versioned migration for the localStorage play library (deferred out of v1 entirely per the plan, not a Phase 7 item). The rotation-sheet export always exports the *focused* side's six rotations from whatever camera preset is currently active. There's no per-export camera override, and it hasn't been tried with every camera preset (top-down is the obvious choice for a printable sheet but isn't forced). The Vercel project uses default deployment protection and the team's default domain; no custom domain has been attached.

**Simple mode and guided authoring:** **the formation-mode 3D on-court bench is still hard to actually use, even though the drag mechanism itself was confirmed working this session** (see "Guided authoring, round 2" above for how that was verified) — the real issue is that a bench player's silhouette is small, dim, and often outside the default camera framing entirely, so a user has to know to zoom/orbit out first. Not fixed: either a more forgiving hit-test radius, a camera nudge when entering formation mode with a non-empty bench, or just steering people toward the reliable `BenchPanel` list (drag a chip) / the new Design Play bench section (click-to-swap) instead of the 3D figures. The `pendingTarget`/`SetTarget` overload noted above under "What's built." The Advanced toggle now applies to formation mode too (see above), but formation mode's own Roster/Lineup/Rotation/Validation/Formation/Bench panel content is otherwise unchanged (the on-court bench is additive, not a replacement for `BenchPanel`'s list). The on-court bench doesn't respect `positionOverrides`, so a manually-displaced formation won't move the bench row. Guided-mode player selection is zone-based only in the sense that it reads whichever `onCourtId` is currently rendered; it doesn't yet show a friendly confirmation when clicking a slot with no player assigned to it (nothing bad happens, the click is just silently a no-op since there's no valid `PlayerRef` to select). No guided-mode support for a play's `initial` formation overrides, waypoints (`Movement.via`), or jumps beyond the attack default; all of that is still Advanced-only. `GuidedAuthorPanel`'s own sidebar Bench section is still click-to-select-then-click-to-place, not drag — it was superseded in practice by the on-screen `CourtBenchOverlay` (round 4, real drag-and-drop) but was left in place rather than removed, so the same swap is currently reachable two ways in Design Play. Worth consolidating if the duplication ever causes confusion.

**One serve-receive modeling choice worth knowing about, not a bug:** the default passer speed (`SPEED_CAP_MPS.shuffle`, 2.8 m/s) makes the uncovered fraction read larger than a coach might expect on first look (497 of 660 cells in one live test). That's mathematically consistent with the inputs, just more pessimistic than real match footage might support, since there's no way yet to say "she'll run for it" instead of shuffle. Tune `serveSpeedMps`/`passerSpeedMps`/`serveApexM` in `ServeReceivePanel.tsx` and `SceneCanvas.tsx`'s serve-receive effect if the balance feels off.
